# Developer documentation

This document covers setting the project up from scratch, building it,
managing the containers and volumes, and modifying it. For day-to-day
operation see `USER_DOC.md`.

## 1. Setting up the environment from scratch

### Prerequisites

- A virtual machine running Debian or Ubuntu. The project must be built and
  run inside a VM, as the subject requires.
- Docker Engine and the Docker Compose v2 plugin.
- `make`, `git` and `sudo`.

If Docker is not installed:

```sh
sh tools/install_docker_debian.sh
```

The script adds Docker's official repository, installs the engine and the
Compose plugin, and adds your user to the `docker` group. **Log out and back
in** afterwards, otherwise every `docker` command will need `sudo`.

Check the result:

```sh
docker --version
docker compose version
docker run --rm hello-world
```

### Configuration files

There are two, and neither is versioned.

**`srcs/.env`** is generated by the Makefile from `srcs/.env.example`. It
holds only non-sensitive values:

```ini
DOMAIN_NAME=mobullad.42.fr
DATA_PATH=/home/mobullad/data
MYSQL_DATABASE=wordpress
MYSQL_USER=wpuser
WORDPRESS_DB_HOST=mariadb
WP_TITLE=Inception
WP_ADMIN_USER=bossman
WP_ADMIN_EMAIL=bossman@student.42.fr
WP_USER=morgan
WP_USER_EMAIL=morgan@student.42.fr
```

Compose reads it in two distinct ways, and the difference matters:

- `env_file: .env` injects these variables into the containers, where the
  entrypoint scripts use them.
- Compose also performs `${VARIABLE}` substitution in
  `docker-compose.yml` itself, on the host, before anything starts. This is
  how `${DATA_PATH}` in the volume definitions and `${DOMAIN_NAME}` in the
  NGINX build argument are resolved.

To change a value, edit `srcs/.env` and run `make down && make`. To change a
default for a fresh clone, edit `srcs/.env.example`.

**`secrets/*.txt`** hold the four passwords, one per file, with no trailing
newline. They are created by `tools/gen_secrets.sh`, which the Makefile calls
and which never overwrites an existing file.

```
db_root_password.txt     db_password.txt
wp_admin_password.txt    wp_user_password.txt
```

Compose declares them in its top-level `secrets:` section and mounts them
read-only at `/run/secrets/<name>` inside the containers that need them. The
entrypoint scripts read them with `$(cat /run/secrets/db_password)`.

To use your own password instead of a generated one, write it before the
first `make`:

```sh
mkdir -p secrets
printf 'my-password' > secrets/db_password.txt
```

Use `printf`, not `echo`: `echo` appends a newline and the newline would
become part of the password.

## 2. Building and launching

### With the Makefile

```sh
make            # the default target: up
make up         # generate .env and secrets, create the data dirs, build, start
make build      # build the images without starting anything
make down       # stop and remove the containers, keep the volumes
make stop       # stop without removing
make start      # start again after stop
make re         # fclean then up
make logs       # follow the logs
make ps         # state of the containers
make credentials# print the generated passwords
make clean      # remove the containers and the named volumes
make fclean     # clean + remove the images and /home/mobullad/data
make hosts      # add the domain to /etc/hosts
make help       # list the targets
```

`make up` depends on three preparation targets, in order:

1. `srcs/.env` — copied from the template if missing.
2. `secrets` — runs `tools/gen_secrets.sh`.
3. `dirs` — creates `/home/mobullad/data/{mariadb,wordpress}`, which the
   named volumes need to exist beforehand.

### With docker compose directly

The Makefile is a thin wrapper. Every target maps to a Compose command:

```sh
docker compose -f srcs/docker-compose.yml --env-file srcs/.env up -d --build
docker compose -f srcs/docker-compose.yml --env-file srcs/.env ps
docker compose -f srcs/docker-compose.yml --env-file srcs/.env logs -f nginx
docker compose -f srcs/docker-compose.yml --env-file srcs/.env down
```

Two commands are worth knowing while developing:

```sh
# print the fully resolved configuration, with every variable substituted.
# The first thing to run when a ${VARIABLE} does not behave as expected.
docker compose -f srcs/docker-compose.yml --env-file srcs/.env config

# rebuild and restart one service only
docker compose -f srcs/docker-compose.yml --env-file srcs/.env up -d --build nginx
```

Note that the Compose project is named after the directory holding the
compose file, so it is `srcs`. This is why the volumes appear as
`srcs_mariadb_data` and `srcs_wordpress_data`, and the network as
`srcs_inception`.

## 3. Managing containers, images, volumes and network

### Containers

```sh
docker ps -a                        # all containers, including stopped ones
docker logs -f wordpress            # follow one container's logs
docker exec -it wordpress sh        # a shell inside a running container
docker inspect wordpress            # full state as JSON
docker stats                        # live CPU and memory usage
```

`docker exec -it <container> sh` is the main debugging tool. Useful once
inside:

```sh
# in nginx
nginx -t                            # validate the configuration
cat /etc/nginx/nginx.conf

# in wordpress
wp core version --allow-root
wp user list --allow-root
php-fpm -t                          # validate the php-fpm configuration

# in mariadb
mariadb -u root -p                  # password in secrets/db_root_password.txt
```

### Images

```sh
docker images
docker image inspect nginx:inception
docker history nginx:inception      # the layers, and what each one costs
docker rmi nginx:inception
```

The images are tagged `<service>:inception`. Each image name matches its
service name, as the subject requires, and the `latest` tag is never used.

### Volumes

```sh
docker volume ls
docker volume inspect srcs_wordpress_data
docker volume rm srcs_wordpress_data     # only when no container uses it
```

### Network

```sh
docker network ls
docker network inspect srcs_inception    # lists the attached containers and their IPs
```

To verify that name resolution works inside the network:

```sh
docker exec -it nginx ping -c1 wordpress
docker exec -it wordpress ping -c1 mariadb
```

### Cleaning up

```sh
make fclean                              # what this project provides

# the command the evaluation sheet asks for, which wipes the whole machine
docker stop $(docker ps -qa); docker rm $(docker ps -qa)
docker rmi -f $(docker images -qa); docker volume rm $(docker volume ls -q)
docker network rm $(docker network ls -q) 2>/dev/null
```

## 4. Where the data lives and how it persists

### The two named volumes

| Volume                 | Mounted in             | At                | Contains             |
| ---------------------- | ---------------------- | ----------------- | -------------------- |
| `srcs_mariadb_data`    | `mariadb`              | `/var/lib/mysql`  | The database files   |
| `srcs_wordpress_data`  | `wordpress` and `nginx`| `/var/www/html`   | The WordPress files  |

`srcs_wordpress_data` is mounted by two containers on purpose. NGINX does not
execute PHP: it sends php-fpm a *path* over FastCGI. Both containers must
therefore see the same files at the same location, and a shared named volume
is what provides that.

### Where they are on the host

Both are declared with the `local` driver and `driver_opts` that point at a
host directory:

```yaml
volumes:
  mariadb_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: ${DATA_PATH}/mariadb
```

So the bytes are at:

```
/home/mobullad/data/mariadb      the MariaDB data directory
/home/mobullad/data/wordpress    the WordPress installation
```

These are Docker named volumes, not bind mounts. They are declared in the
top-level `volumes:` section, referenced by name by the services, and listed
by `docker volume ls`; `driver_opts` only tells the local driver where to
keep their contents. This satisfies both requirements in the subject at once:
named volumes, with the data under `/home/<login>/data`.

Confirm it with:

```sh
docker volume inspect srcs_mariadb_data
```

### What persists, and what does not

| Command        | Containers | Images | Volumes | Data on the host |
| -------------- | ---------- | ------ | ------- | ---------------- |
| `make down`    | removed    | kept   | kept    | kept             |
| `make clean`   | removed    | kept   | removed | kept on disk     |
| `make fclean`  | removed    | removed| removed | **deleted**      |

Because the data survives `make down`, the entrypoint scripts must be able to
tell a first start from a later one. They do it by testing the volume:

- `mariadb/tools/init.sh` checks for `/var/lib/mysql/mysql`. If the directory
  exists, the database was already initialised and the script goes straight
  to `exec mariadbd`.
- `wordpress/tools/init.sh` checks for `wp-config.php`. If the file exists,
  WordPress is already installed and the script goes straight to
  `exec php-fpm -F`.

This is what makes the stack survive a reboot of the virtual machine, which
the evaluation explicitly tests.

### Backing up and restoring

```sh
# back up the database
docker exec mariadb mariadb-dump -u root -p"$(cat secrets/db_root_password.txt)" \
    wordpress > backup.sql

# restore it
docker exec -i mariadb mariadb -u root -p"$(cat secrets/db_root_password.txt)" \
    wordpress < backup.sql

# back up the WordPress files
sudo tar czf wordpress-files.tar.gz -C /home/mobullad/data wordpress
```

## 5. Modifying the project

### Changing a service's port

The evaluation asks for a configuration change during the defense, typically
a port. Say NGINX should listen on 8443 instead of 443. Three places must
agree:

1. `srcs/requirements/nginx/conf/nginx.conf` — the two `listen` directives:
   ```nginx
   listen      8443 ssl;
   listen [::]:8443 ssl;
   ```
2. `srcs/docker-compose.yml` — the published port:
   ```yaml
   ports:
     - "8443:8443"
   ```
3. Rebuild, because `nginx.conf` is copied into the image at build time:
   ```sh
   make down && make
   ```

The site is then at `https://mobullad.42.fr:8443`.

Changing php-fpm's port is the same idea, in `conf/www.conf` (`listen =
9001`), in `nginx.conf` (`fastcgi_pass wordpress:9001;`) and in the `expose:`
list. Nothing is published to the host for that one, since it is internal.

### Changing the Alpine version

The subject requires the **penultimate stable** version of Alpine or Debian.
The three Dockerfiles pin it explicitly on their first line:

```dockerfile
FROM alpine:3.20
```

Check the current releases at https://alpinelinux.org/releases/ before the
defense, and if the penultimate one has moved, change that line in all three
Dockerfiles.

One thing must change with it: on Alpine, the PHP packages carry the version
in their name, and each Alpine release ships one PHP version.

| Alpine | PHP packages | `ARG PHP_VER` |
| ------ | ------------ | ------------- |
| 3.19   | `php82-*`    | `82`          |
| 3.20   | `php83-*`    | `83`          |
| 3.21   | `php84-*`    | `84`          |

`srcs/requirements/wordpress/Dockerfile` declares `ARG PHP_VER=83` for
exactly this reason: every package name is built from it, so one line is
enough. Confirm the right value with:

```sh
docker run --rm alpine:3.XX apk search -e 'php8*' | sort
```

### Adding a service

1. Create `srcs/requirements/<service>/` with a `Dockerfile` and, if needed,
   `conf/` and `tools/`.
2. Add the service to `srcs/docker-compose.yml`: `build:`, an
   `image: <service>:inception` whose name matches the service, the
   `inception` network, `restart: unless-stopped`, and a volume or secret if
   it needs one.
3. Add its image to the `IMAGES` variable in the Makefile so that `fclean`
   removes it.

Bonus services must follow the same rules as the mandatory ones: one
Dockerfile each, built from the same base image, no ready-made image, and a
daemon in the foreground.

## 6. Conventions to respect

These come straight from the subject, and breaking one of them ends the
evaluation.

- One Dockerfile per service, written for this project. No image pulled from
  Docker Hub other than the Alpine base.
- Every Dockerfile starts from the penultimate stable Alpine or Debian. The
  `latest` tag is forbidden.
- Each image is named after its service.
- No password in any Dockerfile. Configuration goes through `.env`,
  credentials through Docker secrets.
- No `network_mode: host`, no `links:`, no `--link`. A `networks:` section is
  mandatory.
- No infinite loop and no background process as an entrypoint: no `tail -f`,
  no `sleep infinity`, no `while true`, no `nginx & bash`. Each container
  runs its daemon in the foreground, and each entrypoint script ends with
  `exec`.
- NGINX is the only entry point, on port 443, with TLSv1.2 or TLSv1.3 only.
- No NGINX in the WordPress or MariaDB images.
- Two WordPress users, one of them the administrator, whose name contains
  neither `admin` nor `administrator`.
- The containers restart on crash (`restart: unless-stopped`).
- No credential committed to the repository, in any form.
